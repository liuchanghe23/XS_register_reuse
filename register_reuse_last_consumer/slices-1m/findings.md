# 最后消费者扩展：初步结论

已完成 8 个 workload 各一个最高权重切片、两种容量的 16 次真实运行；每次预热 1M + 测量 1M，全部 NEMU difftest 通过。所有运行的指令数与模拟周期都和原 OFF 实验完全一致。这是被动应用空间分析，还没有实现或测量扩展后的 IPC。

结论：存在新增机会，主要是整数寄存器；数量最多的程序不一定最受益。优先用 gcc 的寄存器紧张切片验证，mcf 使用缩容点作为补充。先实现“先前消费者均已提交”的保守版本，比直接依赖 WB/readDone 代理更容易验证。

下表是新增候选占实际测量指令的比例。保守版本只承认 prior commit；受限 WB 还承认普通、非访存/非控制标量消费者已写回。二者都保留原版本/shadow 恢复约束。

为什么不能直接等同于加速：

- mcf 新增约 1.9% 的指令可作为候选，默认容量只有 2 个周期与同类不足重叠；192/208 时为 12,468 个周期。
- bwaves 的新增约 0.85% 候选全部是 INT，而该窗口主要是 FP 压力；同类型不足重叠为 0。
- bzip2 的新增约 1.08% 候选也主要是 INT，但与不足的寄存器周期交集很少：默认 191、缩容 338。
- gcc 只有约 0.035%–0.038% 的新增受限 WB 候选，但占位区间与 INT 不足的交集更明显。每类内部去重后的交集为默认 48,312、缩容 59,706 个周期。这是 baseline 上的共现，不能当作扩展后可回收周期。

真实指令示例：mcf 的 PC `0x10a60: c_add a5,a0`，旧 a5 先前已被一个分支和四个 load 读取；示例中这些消费者最晚在重定义 rename 前 12 个周期提交。现有唯一消费者条件会排除它，保守最后消费者扩展可以考虑它。完整 seq/时刻在该运行的 `opportunities.json`。

边界：尚未施加扩展后的版本上限、shadow 容量、端口和调度反馈；没有面积/能耗结论。现有 O3PipeView 的融合指令时间记录不完整，libquantum 架构指令覆盖约 77.57%、gcc 约 99.7%，相关不确定样本保守排除；其余切片约 99.95% 以上。只代表所选切片。

证据：`opportunity-summary/report.md`、`opportunity-summary/per_run.csv`、各点 `opportunities.json`、`validation.json` 和 `timing-equivalence.json`。
